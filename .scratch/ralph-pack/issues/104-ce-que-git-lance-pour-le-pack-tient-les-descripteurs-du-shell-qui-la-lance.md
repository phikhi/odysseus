# 104 — Ce que git lance pour le pack tient les descripteurs du shell qui l'a lancé

**What to build:** Qu'aucun programme que git lance **pour le pack** — un hook *configuré* (`hook.<nom>.command`), un `core.fsmonitor`, ou toute autre clé de la liste de [46] qui nomme un programme — ne tienne un descripteur du shell qui a lancé git au-dessus de stderr, quelle que soit la source de la configuration (dépôt, `~/.gitconfig`, include) et quel que soit `MAX_PARALLEL`. [102] a éteint le **répertoire** de hooks pour tout git du run ; git n'a aucune clé qui éteigne tous les hooks **configurés** (une par nom, et le nom est celui de qui l'écrit), et [46] ne remet une clé qu'**après** la session et seulement dans la configuration **du dépôt**.

**Blocked by:** None

**Write-surface:** `.claude/lib/proc.sh`, `.claude/lib/gate.sh`, `.claude/lib/concurrency.sh`, `.claude/lib/failures.sh`, `.claude/lib/forge.sh`, `.claude/lib/tracker-local.sh`, `.claude/lib/router.sh`, `.claude/lib/lang.sh`, `.claude/lib/forensic.sh`, `.claude/lib/state.sh`, `.claude/lib/receipt.sh`, `.claude/loop.sh`, `test/proc.bats`, `test/gate.bats`, `test/canary.bats`, `test/receipt.bats`, `test/mutate.sh`, `docs/frontiere-de-confiance.md`

**Status:** needs-triage

[46] le remet ensuite et le nomme dans l'itération de 01 ; 02 n'en sait rien ;
  - **C3** — `~/.gitconfig`, hook configuré, `MAX_PARALLEL=1` : [46] le nomme « could not put it back », le run s'arrête en 4, et entre-temps **24 lignes forgées** dans le reçu de 01 (fd 5, 9) ;
  - **C4** — `core.fsmonitor` dans `~/.gitconfig`, `MAX_PARALLEL=1` — une clé que [46] surveille depuis le 29/08, et le même résidu : **978 exécutions, 204 lignes forgées** dans le reçu de 01, fds **3** (`monitor_watch`), **5** (reçu), **6** (prompt d'une lentille, bout lecteur) et **9** (notes du gate).
- [ ] **La sortie est instruite et mesurée.** Candidate : chaque git que le pack lance est exec'd ne tenant rien au-dessus de stderr — la forme de `proc_exec_bare` ([101]), **sans** la remise d'environnement (le jeton de [102] doit rester). Deux formes à peser :
  - une fonction par laquelle passent **tous** les appels (`proc_git …`, ou un nom mieux choisi), tenue par un test dérivé du lexeur de [91] : aucun `git` nu en position de commande dans le pack. ~94 sites, et **~46 entrées de mutation citent une ligne `git`** — le re-ancrage est une partie du ticket, pas une suite ;
  - seulement les verbes qui lancent un programme — mais la liste n'est pas celle des hooks : `core.fsmonitor` tourne à chaque **rafraîchissement d'index**, donc sur des verbes que `h1` trouve muets pour les hooks (`status`, `diff` contre l'arbre de travail, `ls-files` ?). À mesurer verbe par verbe ([51]) avant de choisir, et une liste se dérive ou ne s'écrit pas.
  Faits bash 3.2.57 déjà mesurés pour la forme « fonction » : `VAR=x f` exporte `VAR` aux enfants de `f` pendant l'appel et l'efface ensuite, donc `GIT_INDEX_FILE=… proc_git …` garde sa sémantique ; `( … exec … )` garde le statut. Coût à mesurer : un fork de sous-shell et 253 fermetures (0,8 ms mesurés par [101]) par appel, sur un run qui en fait des centaines.
- [ ] **Ce que ça laisse est écrit** : un programme que git lance tient encore l'environnement exporté du pack, tourne à l'instant que le pack a choisi, et peut faire échouer une transaction (`reference-transaction` → `aborted`) — ce qu'une session peut déjà faire autrement (un `.lock`), à vérifier et à dire.
- [ ] Le **`skip` du canari** posé par [102] est levé : `test/canary.bats`, « a hook a session configures never runs for a sibling iteration in flight » — ou réécrit si la garantie livrée est « ne tient rien » plutôt que « ne tourne pas », avec la raison.
- [ ] Les **phrases** : la provenance que le reçu imprime (l'exception [104]), l'en-tête de `receipt.sh`, les lignes 35, 47, 48 et 65 du tableau, et la clause de [46] « C'est fail-closed et bruyant » qui ne disait pas que le programme tenait les descripteurs.
- [ ] **Question pour la décision, pas pour ce ticket seul** : une fois que rien de ce que git lance ne tient quoi que ce soit, le jeton de [102] reste-t-il ? Il coûte le `pre-push` de git-lfs sur un backend forge — les objets LFS ne sont pas téléversés par le push du pack, et rien ne le dit. Ne pas le retirer sans avoir mesuré ce qu'un hook achète encore.

## Comments

- **Ouvert le 01/10/2026 en livrant [102]**, par la question 5 de la DoD posée au mécanisme que [102] livrait : le jeton `core.hooksPath=/dev/null` éteint le répertoire, et la sonde `h1` a montré que les hooks **configurés** de git 2.54 tirent sur les mêmes évènements, jeton posé. [102] les a mis sur la liste de [46] (`hook.*`) — ce qui les tient à `MAX_PARALLEL=1` (mesuré `C1` : aucune exécution pour le pack, la remise passe avant le premier git de l'itération qui écrive un index ou une ref) et nulle part ailleurs. La sonde `C4` a été écrite pour savoir si c'était un trou neuf : ce n'en est pas un, c'est le résidu de [46] (« une valeur qui répond encore après l'unset ») mesuré pour la première fois **avec ses descripteurs**.

- **Pourquoi c'est une autre classe que [102]** : [102] change ce que git *lit* (le répertoire), ce ticket change ce que tient ce que git *lance*. Le premier a une réponse dans l'environnement, sans toucher un site d'appel ; le second n'en a pas — bash 3.2 ne sait pas poser close-on-exec sur un descripteur qu'il a ouvert — et touche chaque appel, ou chaque verbe qui lance.
