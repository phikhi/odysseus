# 102 — Git exécute pour le pack les hooks que la session pose

**What to build:** Que les appels git du pack ne lancent aucun programme qu'une session a pu écrire dans le répertoire git commun, ou que chacun de ces appels dise ce qu'il lance. Aujourd'hui `$(git rev-parse --git-common-dir)/hooks/` est atteignable depuis n'importe quelle session, rien ne le regarde, et git y exécute des hooks **dans l'arbre de process du pilote et des itérations**, avec leurs descripteurs.

**Blocked by:** None

**Write-surface:** `.claude/lib/gate.sh`, `.claude/lib/concurrency.sh`, `.claude/lib/failures.sh`, `.claude/lib/forge.sh`, `.claude/lib/state.sh`, `.claude/loop.sh`, `test/gate.bats`, `test/concurrency.bats`, `test/failures.bats`, `test/canary.bats`, `test/mutate.sh`, `docs/frontiere-de-confiance.md`

**Status:** resolved

- [x] **Le recensement des hooks que les appels git du pack déclenchent est mesuré, pas raisonné**, verbe par verbe (la règle de [51] : « sonder le verbe, pas la famille »). Déjà mesuré au 29/09 sur git 2.54 : `update-ref` lance `reference-transaction` (commit durable, ref `failed/<ticket>`, fold — `failures.sh`, `concurrency.sh`) ; `git worktree add` lance `post-checkout` (`concurrency_worktree_add`, **dans le pilote**, à chaque itération) ; `git add` **même sous `GIT_INDEX_FILE`**, `write-tree` et `update-index` lancent `post-index-change` (tous les instantanés d'arbre : `gate_tree_snapshot`, les gardes du tracker) ; `git push` lance `pre-push` (`forge.sh`, reçu d'un backend forge). À compléter, et à dériver des appels du pack plutôt que de cette liste.
- [x] **Ces appels n'exécutent plus un hook posé dans le répertoire commun**, ou chaque exception est écrite avec ce qui la tient. Sortie candidate mesurée : `-c core.hooksPath=/dev/null` éteint `reference-transaction` sur un `update-ref`. À trancher : une option par appel, un `GIT_CONFIG_*` d'environnement (qui atteindrait aussi le git de la session et de la commande de test du projet — ce n'est pas le même geste), ou un témoin sur le répertoire.
- [x] **La phrase de `gate.sh` qui dit le contraire est corrigée** (`gate_config_keys`) : « `core.hooksPath` does nothing today because `failures_make_durable` commits with plumbing on purpose ». La plomberie ne protège pas : `update-ref` en est, et lance `reference-transaction`. [46] a regardé la **clé** `core.hooksPath` et pas le **répertoire par défaut**, qui n'a pas besoin de clé.
- [x] La ligne du tableau est écrite. Ce qu'un hook achète n'est pas « exécuter du code » — la session le peut déjà — mais **être un descendant** du pilote ou d'une itération : il tient leurs descripteurs (le canal du reçu de [96], celui de [98]), il échappe au balayage du groupe de la session ([92], [95]), et il survit au run.
- [x] Témoin appairé (le même run sans hook posé) et survivant réel ; le canari reçoit le cas qui décide ; une entrée de mutation par garantie.

- **Mesuré dans le vrai pack** (`f2-le-canal-herite.bats`, L3). La session du ticket 01 écrit `reference-transaction` et `post-checkout` dans `$(git rev-parse --git-common-dir)/hooks/` — un chemin qu'un worktree atteint sans rien faire, les refs et les hooks vivant dans le répertoire commun. Ce qui s'en suit, sur un run à deux tickets :
  - `reference-transaction` tourne à chaque `update-ref` du pack — `preparing`, `prepared`, `committed`, et `aborted` sur un fold refusé — avec le **fd 5 de l'itération ouvert** : le bout écrivain du canal du reçu ([96]) ;
  - il écrit `- FORGED-BY-A-HOOK-ON-FD-5` **six fois dans le reçu de 01 et trois fois dans celui de 02**, dont la session n'a rien posé : le hook survit à l'itération qui l'a écrit, et au run ;
  - `post-checkout` tourne au `git worktree add` du ticket 02, dans l'arbre de process du **pilote**.

- **Un fait de plomberie pour la sortie** : `post-index-change` tourne sur un `git add` sous `GIT_INDEX_FILE`, sur `write-tree` et sur `update-index` (mesuré hors du pack) — donc dans les branches du gate qui prennent un instantané, pas seulement dans l'itération. La surface est plus large que les trois appels qui écrivent une ref.

- **Pourquoi avant [98]** : le canal de [98] est tenu par l'itération pendant toute sa vie, et un hook que git lance pour elle en hérite. [101] fait fermer les descripteurs aux deux points où le pack lance un programme étranger ; git n'est pas un de ces deux points — il est lancé partout, par le pack lui-même — et c'est ce qui fait de ce ticket une autre classe et pas un troisième site de [101].

- **La question 5, posée avant d'écrire, et ce qu'elle a rendu.** *Qu'est-ce qu'une session peut écrire que rien ne vérifie ?* Le répertoire `hooks/` du répertoire commun, mais aussi — trouvé par `h1` et absent du ticket — un hook **configuré** : depuis git 2.5x, `hook.<nom>.command` + `hook.<nom>.event` dans n'importe quelle source de configuration (`.git/config` du répertoire commun, `config.worktree`, `~/.gitconfig`, un include). **`core.hooksPath=/dev/null` ne lui fait rien** (mesuré : chaque évènement l'a lancé, jeton posé), git n'a aucune clé qui les éteigne tous (lu dans `hook.c` de v2.54.0 : `hook.<nom>.enabled`, un par nom), et `hook.*` **manquait à la liste de [46]**, dont c'est pourtant le critère mot pour mot. Le jeton, lui, vit dans l'environnement du pilote et de ses forks : une session hérite d'un environnement, jamais d'un shell, et ne peut rien écrire dans celui de son parent ; aucune source de configuration ne renverse la portée ligne de commande (`h3`). Ce qui reste atteignable est écrit plus bas et part en **[104]**.

- **Décisions, écrites pour ne pas être re-litigées :**
  - **L'environnement, pas un `-c` par appel ni une fonction `git`** : la garantie est une propriété du shell — un appel ajouté demain est couvert sans le savoir, le git que git lance aussi — et **aucun site d'appel ne bouge** : ~94 appels, et ~46 entrées de mutation qui citent une ligne `git` auraient dérivé. Une fonction nommée `git` est contraire au recensement des noms ([89]).
  - **`GIT_CONFIG_PARAMETERS` et pas `GIT_CONFIG_COUNT`** : une seule variable à garder et à rendre ; `COUNT` demande git 2.31 et trois variables par clé. La **forme ancienne** `'k=v'` du jeton, lue par tout git ; la valeur de l'opérateur peut être de l'une ou l'autre forme (`h3`).
  - **Les hooks de l'opérateur ne tournent plus pour le git du pack** : c'est le même répertoire, et rien ne distingue un fichier qu'il a posé d'un fichier qu'une session a posé. Coût écrit dans le tableau : le `pre-push` de git-lfs n'accompagne plus le push du backend forge (pointeurs sans objets sur le serveur, rien ne le dit). Rouvert comme question dans [104] : une fois que rien de ce que git lance ne tient quoi que ce soit, le jeton reste-t-il ?
  - **Les hooks configurés de l'opérateur, eux, tournent encore** (ceux d'avant le run sont la ligne de base de [46]) : les éteindre demande leurs noms, et ne fermerait que la variante « une session modifie un nom existant », pas « une session en ajoute un ».
  - **`init.sh` n'est pas armé** : ses verbes ne lancent aucun hook (`h1`), et une entrée de mutation sur un armement là serait VACUOUS. Les `*_TOKEN_CMD` reçoivent l'environnement du pack (commandes de l'opérateur, la décision de [101]).
