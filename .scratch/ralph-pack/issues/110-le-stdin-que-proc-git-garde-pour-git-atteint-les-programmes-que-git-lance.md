# 110 — Le stdin que `proc_git` garde pour git atteint les programmes que git lance

**What to build:** Qu'un programme que git lance **pour le pack** (un `core.fsmonitor`, un hook configuré, un filtre `clean`/`smudge`) ne reçoive pas le stdin de l'appelant — ou que chaque appelant qui ne pipe pas dans git lui donne `/dev/null`. `proc_git` ([104]) ferme 3..255 mais **garde le stdin** (il le doit : `check-ignore --stdin`, `update-index --index-info`, `hash-object --stdin` pipent dedans). Le programme que git lance en hérite ; dans une boucle `while IFS= read -r x; do proc_git <op d'index> …; done <<LIST`, ce stdin est le **reste de LIST**, et le programme peut le vider. C'est le trou stdin de [106], pour git — explicitement laissé à la passe par [106]/[107].

**Blocked by:** None

**Write-surface:** à instruire — `.claude/lib/proc.sh`, `.claude/lib/gate.sh`, `.claude/lib/*.sh` (les boucles `while read … <<LIST` qui appellent `proc_git` sur une op d'index), `test/proc.bats`, `test/gate.bats`, `test/mutate.sh`, `docs/frontiere-de-confiance.md`

**Status:** needs-triage

- [ ] Le recensement, dérivé ([91]) et pas listé : quelles boucles `while … read … done <<LIST` (ou here-string) ont dans leur corps un `proc_git` sur une **op d'index** (`add`, `update-index`, `checkout-index`, `reset`, `status`, `write-tree`) — les seules où git interroge `core.fsmonitor`/les hooks/les filtres. Foyers lus en ouvrant : `gate.sh` `<<FORCED` (force-staging des chemins gardés), `<<CHANGED`, `<<PATHS`, `<<ROLLBACK`, `<<RESTORE`.
- [ ] La forme de la réparation et son prix : un appelant qui **ne pipe pas** dans git doit lui donner `</dev/null` (la forme que `proc_group_fork` donne à `TEST_CMD`) ; le seul qui pipe (`gate_newly_hidden` : `printf … | proc_git check-ignore --stdin`, `gate.sh:2857`) ne peut pas — là git ET le programme lancé lisent le **même** tuyau et se le disputent, c'est un autre cas, à dire. `proc_git` ne peut pas fermer son propre stdin (des appelants le remplissent) : la discipline est **par appelant**, ou une variante de `proc_git` qui annule stdin pour qui ne pipe pas.
- [ ] La garantie de [104] remise d'accord avec ce qui est vrai : son commentaire dit « nothing a program git starts could inherit, whatever named it, at any MAX_PARALLEL » — **faux de fd 0**. Le commentaire de `proc_git` dit « stdin, stdout and stderr are the caller's » : vrai de git, le trou est que le programme que git **lance** en hérite aussi.
- [ ] Témoin appairé, une entrée de mutation par garantie, la ligne du tableau (ligne 49, `proc_git`) corrigée : ce qu'elle tient au-dessus de stderr, et ce qu'elle **ne** tient **pas** en-dessous (fd 0 pour le programme lancé).

## Comments

- **Ouvert par la passe transversale du 16/10/2026** (`../passe-transversale-16-10.md`). Matière (3) de [106] (« le stdin des programmes que git lance pour le pack », laissée non mesurée) et [107].

- **Mesuré hors du pack** (`../../../tmp`… scratchpad `fsmon/probe2.sh`, bash + git Apple, darwin) : un `core.fsmonitor` dans une boucle `while read p; do git add -- ":(literal)$p"; done <<CHANGED` **avale `SENTINEL-line-b`/`SENTINEL-line-c`** — la boucle ne traite que la première entrée. Déterministe : le 1er `git add` établit le token fsmonitor **sans** interroger le programme, le 2e l'interroge et il draine **tout le reste** du heredoc d'un coup → `read` suivant = EOF. Donc les **deux premières** lignes de LIST sont toujours traitées, la 3e et les suivantes sautées.

- **Mesuré dans un vrai run** (sondes `../sondes/passe-16-10/`) :
  - `g1` : une session écrit `core.fsmonitor` dans le `~/.gitconfig` de l'opérateur (valeur qu'aucun `unset` du dépôt n'atteint, [104]) ; sur une nuit, le programme lancé par git **tourne 136 fois et draine 166 lignes** du stdin de git — des données réelles du pack : `.claude/settings.local.json`, `CLAUDE.md`, `.mcp.json`, `learning-records`, `.claude/agents`… (la liste des chemins gardés + scellés du force-staging).
  - `g4` : `GUARDED_PATHS` à trois répertoires (`.claude`, `assets`, `vendor`), `vendor/` ignoré, la session écrit `vendor/rogue` (sous le **3e** chemin gardé, ligne 3 de `<<FORCED`). Témoin sans plant : `vendor/rogue` **nommé** hors-surface, repris. Avec le plant : `vendor/rogue` **n'est plus nommé** — le force-staging du 3e chemin gardé est sauté, **la garde de portée ne le juge plus**. (`g2`/`g3` : les lignes 1-2 — `.claude` et le 1er scellé — restent force-stagées, donc le sceau, qui lit les scellés à part, tient ; le trou est sur la **3e** ligne et au-delà.)

- **Ce qui le tient encore debout aujourd'hui — et pourquoi c'est la trouvaille.** Dans `g4` la nuit reste **rouge** (fichier repris, ticket `ready-for-agent`), non par la garde de portée (défaite) mais parce que **[46] attrape la clé** : `moved core.fsmonitor … this run could not put [it] back` → `delivery=red`. Toutes les clés que git exécute sur une op d'index — `core.fsmonitor`, `filter.*.clean/smudge/process`, `hook.*` — sont dans `gate_config_keys` (`gate.sh:1253`). **Le force-staging de `<<FORCED` est donc tenu par [46], pas par lui-même** : sa justesse est empruntée à une **liste** que [104] a lui-même appelée « a thing that has to be right again tomorrow ». Un faux vert complet (fichier qui survit, ticket résolu) demande une clé qui (a) fait exécuter un programme à git sur une op d'index, (b) draine stdin, (c) n'est **pas** dans `gate_config_keys` — à trancher par le ticket. Fermer le stdin pour le programme lancé rend le force-staging juste **sans** dépendre de cette liste.

- **Question voisine, à dire et pas forcément à fermer ici** : `gate_newly_hidden` pipe la liste des chemins ignorés dans `git check-ignore --stdin` ; là git **lui-même** lit le tuyau, et un programme lancé par ce même git le lit aussi → course. Si le programme vole des lignes, `check-ignore` voit moins de chemins → `gate_newly_hidden` croit que moins de chemins sont cachés → un chemin caché par une règle écrite pendant l'itération n'est pas forcé dans le snapshot. Sur le chemin frontière-bougée ([30]/[100]/[109]).

- **Place dans la file, VALIDÉE par Philippe le 16/10/2026 : [108] → [110] → [109]** (la passe du 16/10 l'a ouvert, détail `../passe-transversale-16-10.md`, §1). Arête neuve **108 → 110**, soft et sans `Blocked by:` : [108] convertit les boucles `while read … <<LIST` (heredocs → expansion de paramètres), [110] donne la discipline de stdin aux `proc_git` de ces mêmes corps — voisins pour ne pas retoucher les mêmes lignes deux fois, mais [110] ferme le stdin par appelant quelle que soit la forme du heredoc. §2 de la passe (une borne muette sur un stderr jeté) est resté **matière écrite**, pas un ticket.

- **Ce que [108] (livré le 16/10/2026) laisse à ce ticket.** Les boucles `while read … done <<LIST` n'existent plus dans le pack : elles sont `proc_lines "$liste"` puis `for x in ${PROC_LINES[@]+"${PROC_LINES[@]}"}`, et leur corps a **le stdin de la fonction appelante**, plus le reste d'une liste. Donc le vecteur mesuré par la passe (un `core.fsmonitor` qui draine le heredoc `<<FORCED` et fait sauter le 3ᵉ chemin gardé, `g4`) **ne se reproduit plus par ce chemin** : `g4` rejouée sur la branche de [108], `vendor/rogue` est nommé et repris, et le programme lancé par git a lu **3 lignes** — d'où, c'est la première mesure de ce ticket (stdin de l'itération dans `test/run.sh … </dev/null` : à vérifier). Ce qui reste vrai et est l'objet de ce ticket : `proc_git` garde fd 0, et ce qu'il porte au moment de l'appel (terminal d'un humain au drain, socket, `/dev/null` en AFK selon le lanceur) atteint le programme que git lance. Le `</dev/null` aux `proc_git` qui ne pipent pas reste la forme ; les sites sont maintenant dans des `for`, pas des `while read`.
