# 24 — La zone morte des fichiers ignorés par git

**What to build:** Fermer, ou déclarer explicitement, la zone que `.gitignore` soustrait à **tous** les contrôles du pack. `gate_tree_snapshot` sans argument fait `git add -A` **sans** `--force` : ce qu'un projet ignore n'entre pas dans le tree, donc le scope-guard ne le voit pas, le rollback ne le défait pas, et il survit d'itération en itération. Une session peut donc écrire hors de sa write-surface, garder son écriture après un gate rouge, et laisser derrière elle un fichier qui change le verdict des tickets suivants.

**Blocked by:** None

**Write-surface:** `.claude/lib/gate.sh`, `.claude/lib/failures.sh`, `.claude/ralph.config.sh.example`, `test/gate.bats`, `test/failures.bats`, `test/mutate.sh`, `docs/frontiere-de-confiance.md`, `CONTEXT.md`, `README.md`, `test/canary.bats`

**Status:** resolved

- [x] Une session qui écrit un fichier couvert par `.gitignore`, hors de sa write-surface, ne rend pas une itération verte : soit le scope-guard le voit, soit le pack déclare la zone et dit qui la garde. *Les deux, selon le chemin : sous `GUARDED_PATHS` le scope-guard le voit (snapshot forcé) ; ailleurs la zone est déclarée, nommée à chaque itération, et son propriétaire est [13].*
- [x] Le rollback rend un verdict honnête sur cette zone : il la défait, ou il dit ce qu'il n'a pas défait. « L'arbre est remis où la session l'a trouvé » ne doit pas rester vrai à l'exception d'un ensemble de chemins que personne n'énumère. *Il défait les chemins gardés et énumère le reste — `this rollback could not undo N ignored path(s)` — même quand il n'a rien eu à défaire, ce qui est justement le cas où le silence mentirait.*
- [x] Le cas armé est couvert : un `.claude/settings.local.json` déposé par une session ne s'applique pas aux sessions suivantes du run — ou bien le pack le neutralise à chaque spawn, comme il le fait déjà pour `DISABLE_AUTO_COMPACT`. *Première branche, par le scellement : aucune write-surface ne peut le couvrir, l'itération est rouge, le rollback l'efface. Témoin écrit par la session elle-même : la seconde session ne le voit pas. La neutralisation au spawn a été déroulée puis écartée — voir la livraison.*
- [x] Le choix est écrit dans `ralph.config.sh.example` avec son coût : tirer les fichiers ignorés dans le snapshot ferait ressembler chaque build à un débordement, et c'est la raison pour laquelle `git add -A` est sans `--force` aujourd'hui. *Section « The zone git does not show », avec le coût, l'échappatoire, et ce que la clé ne peut pas éteindre.*
- [x] La ligne correspondante de `docs/frontiere-de-confiance.md` existe et ne dit pas « Rien » sans nommer son propriétaire. *Trois lignes : ce que le scope-guard tient maintenant, le scellement, et la zone qui reste — « rien ne le juge, mais plus rien ne le tait », propriétaires [13] et [10].*

## Comments

- **Origine : passe transversale 01→22, le 29/07/2026.** Trouvé en posant la question 5 sur `gate_tree_snapshot`, et sondé pour de vrai avec un projet portant un `.gitignore` — c'est-à-dire tout projet réel. Trois sondes, trois confirmations :

  - Une session écrit `src/alpha.txt` (dans sa surface) **et** `cache/payload` (hors surface, ignoré). Verdict du gate : `tests=green typecheck=green scope=green`, ticket `resolved`. Le scope-guard n'a rien vu.
  - Même session, `TEST_CMD` rouge donc rollback : `src/alpha.txt` est bien défait, `cache/payload` **reste**. Le rollback ne peut pas défaire ce que le snapshot ne contient pas.
  - Deux tickets à la suite. La session de `01-alpha` dépose `cache/unlock`. `TEST_CMD` du projet lit `cache/unlock` — ce que fait n'importe quelle suite qui dépend d'un `.env`, d'un cache de fixtures, d'une base de test ou de `node_modules`. `02-beta` passe au vert **grâce au fichier que 01 a laissé**, et les deux tickets sont marqués `resolved`. C'est la question 4 dans sa forme la plus pure : le défaut n'est faux dans aucun des deux tickets pris isolément.

- **Le cas armé, et c'est lui qui fait la gravité.** `.claude/settings.local.json` est ignoré par convention dans tout projet Claude Code. Sondé : une session écrit ce fichier avec un hook `PreToolUse`, le gate rend `scope=green`, le ticket est `resolved`, et le fichier est encore là. Toutes les sessions suivantes du run l'héritent — c'est-à-dire qu'une session peut configurer le harnais qui juge ses successeurs. Le commentaire de `session.sh` a déjà eu cette inquiétude pour un cas précis (« `DISABLE_AUTO_COMPACT` est posé ici *et* dans settings.json : la garantie ne doit pas dépendre d'un fichier de réglages que le projet cible pourrait écraser ») et la réponse était bonne pour l'auto-compact seul. Elle ne couvre ni les hooks, ni les permissions, ni le reste.

- **Ne pas « réparer » ça en mettant `--force` partout.** Le commentaire de `gate_tree_snapshot` dit exactement pourquoi le snapshot d'arbre entier est sans `--force` : tirer le build output d'un projet dedans ferait déclarer chaque itération en débordement. Le chemin avec arguments force déjà (`failures_tracker_tree` s'en sert, et c'est ce qui rend la protection du tracker de [21] insensible à un projet qui ignore `.scratch/`). Deux pistes plausibles, à trancher dans le ticket : un ensemble de chemins **sensibles** explicitement forcés dans le snapshot (`.claude/`, la config, ce que le projet déclare), ou un contrôle séparé qui compare la liste des fichiers ignorés avant et après la session. La seconde voit tout mais coûte un parcours ; la première ne voit que ce qu'on a pensé à nommer.

- **Contrainte pour qui livrera ça : le tracker vit dans la zone ignorée, en partie.** Le `.gitignore` de ce dépôt ignore `.scratch/*/run.log`, `.scratch/*/.run.lock/` et `.scratch/*/.session.*.jsonl`, et [19] les provisionne dans les projets cibles. Un contrôle qui rendrait « tout fichier ignoré » rouge ferait donc rougir chaque itération sur le journal de run et le flux de session, qui s'écrivent *pendant* la fenêtre surveillée. La zone à garder est « ignoré **et** hors du bookkeeping de la feature », et `gate_is_bookkeeping` est déjà l'endroit qui sait le dire.

- **Constaté au passage, à ne pas confondre avec ce ticket.** Le pack n'a aucun contrôle sur ce qu'une session écrit *hors du dépôt* — `$HOME`, `/tmp`, un autre dépôt sur la machine. C'est hors de portée d'un scope-guard qui diffe des trees git, ce n'est pas ce ticket, et le seul rempart est `--dangerously-skip-permissions` assumé au niveau du pack. À écrire dans le tableau de la frontière comme une limite, pas comme un trou à combler.

## Livraison — 29/07/2026

**Ce qui a été tranché entre les deux pistes.** Les deux, mais pas au même titre, parce qu'elles ne répondent pas à la même question.

- **Piste 1, les chemins nommés** (`GUARDED_PATHS`, défaut `.claude`) : `gate_tree_snapshot` sans pathspec fait toujours un `git add -A` ordinaire, puis force chaque chemin gardé par-dessus, dans le même index jetable. Le scope-guard les voit, le rollback les défait, un projet qui ignore `.claude/` en entier ne soustrait plus le pack lui-même aux deux contrôles. C'est le contrôle.
- **Piste 2, la comparaison des fichiers ignorés** : retenue, mais **comme énumération et pas comme verdict**. `gate_unguarded_ignored` liste ce que le `.gitignore` du projet couvre en dehors des chemins gardés (répertoires repliés par `--directory`, bookkeeping de la feature exclu) et deux lecteurs le disent à voix haute — le gate à chaque itération (`nothing in this gate judged N ignored path(s)`), le rollback à chaque fois qu'il n'a pas tout défait (`this rollback could not undo N ignored path(s)`).

  La rendre rouge était impossible : sur un vrai projet, la session lance la suite de tests, donc la moitié de `dist/`, `coverage/` et `node_modules/.cache` apparaît dans le delta de *chaque* itération honnête. Un contrôle qui rougit partout n'est pas un contrôle, c'est un run qui ne broie rien. La nommer coûte une ligne et donne au lecteur du matin ce qu'aucun document ne lui donnera : la zone, à chaque tour, avec son compte.

**Le scellement, qui est la vraie réponse au cas armé.** Forcer `.claude` dans le snapshot ne suffisait pas : il restait la moitié « une write-surface qui déclare le fichier ». Trois fichiers ne peuvent donc être couverts par **aucune** write-surface, et la question est posée *avant* celle de la surface (`gate_is_sealed` dans `gate__scope_guard`) : `.claude/settings.local.json`, `.claude/settings.json`, `.claude/ralph.config.sh`. Le critère n'est pas « c'est important » mais **« un `claude` frais le lit au démarrage, ou le run suivant le source »** — hooks, permissions, env prennent effet au spawn suivant, et `ralph.config.sh` porte `TEST_CMD`. Ils sont forcés dans le snapshot quoi que dise `GUARDED_PATHS` : une garantie qu'une clé de config peut vider n'est pas une garantie.

Le **code** du pack n'est pas scellé, à dessein, et c'est la frontière à ne pas déplacer sans y penser : un run a sourcé ses libs avant sa première session, donc réécrire `gate.sh` ne change pas le jugement du run en cours, et un ticket qui réécrit `gate.sh` est exactement ce que ce dépôt fait de lui-même. Ce qu'un `claude` frais lit est l'autre question — ça atterrit au spawn suivant, en silence.

**Pourquoi le pack ne neutralise pas la config à chaque spawn** (la seconde branche de l'AC). C'était l'autre voie, sur le modèle de `DISABLE_AUTO_COMPACT` : épingler le contenu au démarrage du run et le réécrire avant chaque spawn. Écartée après l'avoir déroulée, pour deux raisons.

1. **Elle déplace le poison au lieu de l'effacer.** Épingler « ce qui est sur le disque au démarrage » veut dire qu'un run suivant épingle ce que le dernier run a laissé — la configuration hostile devient permanente au lieu d'être annulée. Il faut de toute façon quelque chose qui la retire, et ce quelque chose est le couple scope-guard + rollback.
2. **Le placement était un piège.** La restauration doit tomber **avant** le snapshot `base` de l'itération, sinon la remise en état devient elle-même un delta imputé à la session — donc un `scope=red` pour un fichier que la session n'a pas touché. Ça obligeait à toucher `loop.sh` et `session.sh` pour une garantie que le scellement donne déjà, sans fenêtre.

Consigné parce que c'est un arbitrage et pas une omission : si un jour un `claude` réel écrit `settings.local.json` de lui-même en mode `bypassPermissions` (il le fait en interactif, pour enregistrer un « always allow »), le scellement le rendrait rouge à chaque itération. Le symptôme serait immédiat et nommé (`wrote .claude/settings.local.json, which configures the harness itself`) sur la première itération, pas silencieux — et l'échappatoire est là. **Non vérifié contre le vrai binaire** : `RALPH_REAL_CLAUDE=1` n'a pas été rejoué ici. C'est la seule inconnue que cette livraison laisse, et c'est celle-là qu'il faut sonder si un run réel rougit partout.

**Sondes rejouées, avec les trois d'origine.**

- *Fichier ignoré sous un chemin gardé* : un projet ignore `.claude/cache/`, la session écrit `src/alpha.txt` (dans sa surface) et `.claude/cache/rogue`. Avant : `scope=green`, `resolved`, fichier toujours là. Après : `scope=red`, ticket en frontière, fichier effacé. Test `an ignored file under a guarded path is caught and undone all the same`.

Sondé : les deux sont nommés (`outside the declared write-surface` pour la lib, `configures the harness itself` pour la config), le rollback défait 3 chemins, `gate.sh` retrouve sa dernière ligne, la config a disparu. Avant [24] : rien. Une session pouvait réécrire le gate qui juge le run suivant.
- *Le cas armé, avec témoin* : un ticket **déclare** `.claude/settings.local.json` dans sa write-surface, la session y dépose un hook `PreToolUse`, et le fake enregistre à chaque spawn s'il voit le fichier. La première tentative est rouge, le rollback efface, la seconde session **ne voit rien** et livre le ticket. Test `a session cannot configure the harness that judges the next one` — c'est le seul test du dépôt qui asserte l'absence d'héritage entre deux sessions par un témoin écrit par la session elle-même.

Le rollback ne trouve rien dans son diff — et le dit quand même, parce que c'est précisément le cas où « l'arbre est remis où la session l'a trouvé » est faux. Test `a rollback with nothing to undo names the zone all the same`.
- *La question 4 dans sa forme pure* : `TEST_CMD='test -e cache/unlock'`, `01-alpha` dépose `cache/unlock`, `02-beta` n'écrit que dans sa surface et passe au vert **grâce au fichier de 01**. Les deux `resolved`, et le pack ne peut pas le voir. Ce qui a changé : il le nomme, sur l'itération qui en a bénéficié. **Le piège central, et il est tenu par un test.** La zone à garder est « ignoré **et** hors du bookkeeping de la feature ». `run.log`, `.run.lock/` et les flux `.session.*.jsonl` sont ignorés par [19] **et** s'écrivent pendant la fenêtre surveillée : une énumération qui les compte rapporte les écritures de la boucle comme des écritures de session, à chaque itération de chaque projet. `gate_is_bookkeeping` est le seul endroit qui sait le dire — une définition, **trois** lecteurs maintenant (le filtre du scope-guard, le rollback, l'énumération), et la mutation `24 the loop's own bookkeeping counts as an unjudged write` existe pour qu'un quatrième lecteur ne réécrive pas la règle à côté.

Le piège symétrique, celui qu'on ne pense pas à couvrir : **nommer un chemin que le gate a bien jugé** est un mensonge dans l'autre sens. Tenu par deux refutations dans le test du chemin gardé, sur un projet dont le *seul* chemin ignoré est un chemin gardé — sinon la refutation passerait sur la foi d'un autre chemin, ce que ce dépôt a déjà raté une fois.

**Asymétrie assumée : gardé ne veut pas dire commité.** Sondé — un ticket dont la write-surface est un chemin que le projet ignore passe au vert, et `failures_make_durable` ne le commite pas : son `git add` est sans `--force`, donc git refuse un fichier ignoré, `newtree` égale l'arbre de `HEAD` et la fonction sort par « rien à enregistrer ». Le travail vit dans l'arbre de travail et nulle part ailleurs. C'est le bon arbitrage — commiter un fichier que le projet a explicitement ignoré serait contredire le projet, et c'est comme ça qu'un `settings.local.json` de machine finirait dans l'historique — et le rollback reste correct puisqu'il restaure depuis le **tree** pré-session et non depuis `HEAD`. Écrit ici parce que rien dans le code ne le dit, et écrit dans [19] parce que c'est l'installeur qui élargira cette zone.

Un doc qui contredit le code est un mensonge — mais l'élargissement se déclare.

Le canari mérite son paragraphe, parce que c'est la trouvaille de plus. Son en-tête annonce « le monde tel qu'il est plutôt que tel que les fixtures le souhaiteraient » — et son monde hostile n'avait **pas de `.gitignore`**, pendant vingt-deux tickets. C'est précisément l'écart où cette zone morte a vécu : tout projet réel en a un, et c'est ce fichier-là qui décide de ce que n'importe quel contrôle du pack peut voir. Le monde hostile porte maintenant un cache de build hors de git, et deux assertions de plus : le run **nomme** la zone à chacune de ses trois itérations vertes (trois verts sur un projet avec un `.gitignore` sont trois verts avec un astérisque, et l'astérisque doit être imprimé, pas retenu), et le cache existant est intact à la fin. ## Relu par la passe transversale 24→26, le 30/07/2026

Trois trouvailles dans ce livrable, toutes dans la moitié « déclarer la zone » plutôt que dans le contrôle.

- **La question posée était incomplète, ouverte en [30].** Ce ticket a écrit qu'« un contrôle qui délègue sa visibilité à un fichier que le projet écrit doit dire jusqu'où il voit ». La moitié manquante est **qui écrit ce fichier** : une session peut ajouter une règle à `.git/info/exclude` (aucune write-surface nécessaire — rien dans le pack ne regarde `.git/`) ou à un `.gitignore` que son ticket déclare, et écrire hors surface derrière. Sondé : deux itérations vertes, les fichiers en place, zéro plainte du scope-guard, et sur le chemin `.gitignore` la boucle **commite la règle**. La ligne de zone nomme bien la conséquence ; elle ne dit pas que c'est la session qui a déplacé la frontière.
- **La ligne de zone nomme le tracker, qui est jugé, ouvert en [30].** Un projet qui ignore `.scratch/` sans avoir commité le tracker obtient `nothing in this gate judged 1 ignored path(s): .scratch/` — faux, `failures_tracker_tree` le snapshotte avec `--force` ([21]). `git ls-files --directory` replie le répertoire, et `gate_is_bookkeeping` ne reconnaît que `.scratch/<feature>/*`. C'est le mensonge symétrique que ce ticket avait explicitement gardé pour les chemins gardés, et laissé ouvert pour celui-là.
- **Le scellement est plus étroit que le critère écrit à côté, ouvert en [31].** Le critère — « un `claude` frais le lit au démarrage, ou le run suivant le source » — est le bon ; la liste a été écrite depuis le cas qui l'a motivée. `CLAUDE.md` et `.mcp.json` sont lus par chaque spawn, peuvent être déclarés dans une write-surface, sont hérités par la session suivante (témoin écrit par le fake) et sont **commités** par la boucle. Et `RALPH_CONFIG` sous un autre nom n'est pas scellé du tout, ce qui rouvre le trou par une clé d'environnement.

**Ce qui tient, sondé pour ne pas surestimer** : `--force` l'emporte sur toute règle d'ignore, donc une session qui écrit `.claude/` et `.scratch/` dans `.git/info/exclude`, réécrit `gate.sh` et met sa surface à `*` est attrapée sur les trois — le scellement et la protection du tracker ne dépendent pas de ce que le projet ignore. Le trou de [30] est borné à ce qui est hors de `GUARDED_PATHS`.

**Deux trous de plus, ouverts par la passe transversale du 03/08/2026, et le premier est dans ce livrable-ci et pas dans [30].**

- **[33] — refermé le 04/08/2026, et il change ce que « chemin gardé » veut dire.** Toute liste que le pack se passe à lui-même voyage désormais **un chemin par ligne**, `GUARDED_PATHS` comprise — la clé se rédige donc une ligne par chemin, ce qui est écrit dans `ralph.config.sh.example`. Et les chemins gardés et scellés sont lus **littéralement** des deux côtés du mécanisme : pathspecs `:(literal)` au forçage, `gate__under_path` (et non plus `gate_in_surface`) pour l'exclusion de la ligne de zone et pour `gate_is_sealed`. Le prix, assumé et testé : un `GUARDED_PATHS` rédigé comme un glob — `vendor/*` — ne garde plus rien, mais la ligne de zone le nomme au lieu de se taire. La phrase de ce ticket « les chemins gardés sont pris par force » n'était vraie que pour un chemin sans espace ni métacaractère avant cette date. Le constat d'origine :
- **[33] — les chemins gardés sont forcés par un `for path in $(gate_guarded_paths)`.** Un `GUARDED_PATHS` dont un chemin porte une **espace** est découpé en pathspecs qui ne matchent rien, et le `|| true` qui protège le cas légitime (un projet nomme un chemin qu'il n'a pas encore) avale exactement cette erreur. Un projet dont le répertoire gardé porte une espace n'a donc **aucun** garde, depuis ce ticket-ci et non depuis [30] — c'est simplement [30] qui a fait passer une seconde liste par la même boucle, où la sonde l'a trouvé. Et la ligne de zone se taît sur ces chemins, parce qu'elle les exclut par comparaison de chaîne entière : les deux moitiés du mécanisme ne découpent pas la liste de la même façon.
- **[35] — `LENSES` éteint plus que ce que ce ticket a écrit d'elle.** La règle posée ici est qu'une clé de config est un interrupteur et qu'il faut dire ce qu'elle ne peut pas éteindre. `LENSES` annonce éteindre le jugement subjectif — et la boucle le dit à chaque itération, ce qui est le bon comportement. Elle éteint en plus le refus d'un **diff vide** ([06]), qui est déterministe et n'a rien à voir avec le palier : une session qui n'écrit rien est alors `resolved`. La question de ce ticket avait la bonne forme ; il fallait la reposer chaque fois qu'un contrôle déterministe est ajouté à l'intérieur d'un mécanisme optionnel.

## Relu par [50], le 30/08/2026 — l'asymétrie gardé/commité est fermée

Ce ticket a laissé une phrase qui n'était vraie qu'à moitié : « sous `GUARDED_PATHS` le
scope-guard le voit ». Il le voyait, l'approuvait, et le **rollbackait sur rouge** ; sur
vert, `failures_make_durable` faisait `git add` sans `-f` et git refusait le chemin
ignoré. Trois verdicts sur quatre traitaient la zone gardée, le quatrième — le seul où
le travail est censé survivre — ne faisait rien. Sondé au défaut : un projet qui ignore
`.claude/` avec le `GUARDED_PATHS` par défaut sort `resolved` **sans aucun commit ni
fold**, la seule ligne de journal étant la ligne de gap de [39].

Depuis [50], le commit durable stage à travers la même lentille que le snapshot :
`git add -A --force` sur la liste approuvée. Ce que ça change pour ce ticket-ci :

- Le « ne pas réparer ça en mettant `--force` partout » du commentaire ci-dessus reste
  vrai **du snapshot** et n'a jamais valu du **commit**. Les deux listes sont
  différentes : le snapshot force une zone entière, le commit force ce qui est déjà
  dans la liste approuvée — donc déjà jugé, déjà dans la write-surface d'un ticket.
- Le cas armé de ce ticket, `.claude/settings.local.json`, reste hors d'atteinte, et
  c'est le scellement de [31] qui le tient et non le forçage : un chemin scellé n'est
  jamais approuvé, donc jamais dans la liste que le commit force.
- Le prix nouveau, écrit dans `docs/frontiere-de-confiance.md` : un `GUARDED_PATHS`
