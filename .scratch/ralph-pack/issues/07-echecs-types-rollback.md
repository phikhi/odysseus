# 07 — Échecs typés + rollback

**What to build:** La gestion des échecs de la boucle, par type : `too-big` → re-découpage autonome ; gate rouge / crash non-budget → retry-N en session fraîche puis `ready-for-human` ; contractuel → escalade directe. Avec rollback propre du dépôt et raison `Escalation:` posée sur toute escalade.

**Blocked by:** 05

**Write-surface:** `.claude/lib/failures.sh`, `test/failures.bats`, `.claude/loop.sh`, `.claude/lib/gate.sh`, `.claude/lib/tracker.sh`, `.claude/lib/tracker-local.sh`, `.claude/ralph.config.sh.example`, `test/canary.bats`, `test/smart-zone.bats`, `test/gate.bats`, `test/loop-happy-path.bats`, `test/smoke.bats`, `test/mutate.sh`

**Status:** resolved

- [x] Un ticket « too-big » est re-découpé de façon autonome en préservant les AC (via `to-tickets`) et ré-injecté en frontière ; soupape humaine seulement si les AC ne peuvent être préservées.
- [x] Un gate rouge / crash non-budget déclenche jusqu'à `RETRY_N` retries en session fraîche ; au-delà, le ticket passe `ready-for-human` avec le compteur `Failures:` incrémenté.
- [x] Une décision contractuelle escalade directement, sans consommer les retries.
- [x] Rollback : snapshot `HEAD` pré-spawn → `git reset --hard` + `git clean` ; le dépôt est propre après un échec.
- [x] Avant l'escalade finale, une branche `failed/<ticket>` préserve la tentative ; toute escalade pose une ligne `Escalation:` (jeu fermé).
- [x] Un gate vert rend le travail de l'itération **durable** avant l'itération suivante ; un rollback ultérieur ne détruit rien de ce qui a déjà été gaté vert.
- [x] Le débordement d'une tentative ratée n'est plus absous à la tentative suivante (test `skip` du canari levé).

## Comments

- **Contrainte posée par [05] : un gate vert doit commiter.** Aujourd'hui rien ne rend durable le travail d'une itération résolue — il reste non commité dans l'arbre. Le `git reset --hard $PRE` + `git clean -fd` prévu ici **détruirait donc tout ce que le run a produit depuis son démarrage**, pas seulement la tentative ratée. Le rollback n'est correct qu'à partir du moment où chaque itération verte est commitée : le `HEAD` pré-spawn devient alors réellement « l'état d'avant cette itération ». C'est aussi ce qui donnera au reçu d'audit [10] un diff à référencer.
- Le scope-guard, lui, ne dépend plus de ce commit : il compare deux snapshots d'arbre pris autour de la session ([05] a dû le corriger après coup, voir ses commentaires). Mais il reste un `git rev-parse HEAD` pré-spawn à prendre **ici**, pour le rollback — un objet tree n'est pas un commit et ne se `reset --hard` pas.
- **Ce que [05] laisse à câbler ici** : `RALPH_GATE_SCOPE_CLASS` vaut `internal` (write-surface trop étroite → retry-N) ou `contract` (débordement dans la write-surface d'un autre ticket → escalade directe `ready-for-human`, sans consommer de retry, conformément à la décision de discovery [19]). La boucle logge la classe aujourd'hui ; personne n'agit dessus.
- **Trou connu à couvrir** : aucune branche du gate n'a de timeout. Une `TEST_CMD` qui pend fait pendre le run indéfiniment — le filet smart-zone ne surveille que la session. Un échec par timeout est un échec typé de plus.

- **Faille vivante trouvée par le canari hostile, à refermer ici.** Sans rollback, une session peut **battre le scope-guard en échouant une fois**. Reproduit : une session qui écrit `src/rogue.txt` hors de sa write-surface est rouge à l'itération 1 ; le fichier reste dans l'arbre ; à l'itération 2 sur le même ticket, il fait partie de la référence pré-spawn, donc n'est plus imputé — et si la session refait exactement la même chose, le diff est vide et le gate passe **vert**. Ticket `resolved`, fichier fautif toujours là, `exit 0`.

  Non corrigeable depuis le gate : tout ce qui marcherait (mémoriser les débordements entre tentatives, refuser la remise en frontière) duplique la politique d'échec de ce ticket. La cause est qu'aucun mécanisme ne remet l'arbre en état après un gate rouge.

  Le test existe déjà, marqué `skip` dans `test/canary.bats` (« an overflow is not absolved by having already failed once ») : **le lever est un critère d'acceptation de ce ticket**.

## Livraison (28/07/2026)

- **Le rollback n'est pas un `git reset --hard` + `git clean -fd`, et l'AC est livrée en écart assumé.** Le rollback littéral demandé détruit le travail non commité **du dépôt hôte** : `--hard` écrase l'édition en cours d'un humain sur un fichier suivi, `clean -fd` supprime ses fichiers non suivis. Un run AFK lancé le soir sur un poste où quelqu'un a du travail en cours effacerait ce travail au premier gate rouge — un dégât hors périmètre du ticket et irréversible.

  Ce qui est livré à la place est **aussi large que le diff de la session, et pas un octet de plus** : `git diff-tree -r --name-status $base $tree` par chemin, `A` → suppression du fichier, tout le reste → restauration depuis le snapshot pré-session (`git checkout-index -f` sur un index jetable monté par `read-tree`, ce qui préserve modes et symlinks). Le `HEAD` pré-spawn sert au cas « la session a commité » : `git reset --mixed $PRE` remet la branche, l'arbre étant traité par la même restauration chemin par chemin. Vérifié : l'arbre revient **exactement** au tree object pré-session (comparaison de sha), le travail en cours d'un tiers reste tel quel, et un fichier supprimé par la session revient (avec son mode).

  `--mixed` et non `--soft` : l'index doit repartir du commit pré-spawn, sinon ce que la session avait commité resterait stagé. Et pour le cas plus fréquent — une session qui fait `git add` sans commiter, ce que laisse un agent interrompu en plein commit — un `git reset -- <chemins de la session>` désindexe la tentative après la restauration. Sans lui, les fichiers disparaissent de l'arbre mais restent dans l'index, prêts à partir avec le prochain commit ; le test l'attrape via `git status`. Le désindexage est **borné aux chemins de la session**, donc un index qu'un humain avait préparé ailleurs tient bon. Perte assumée : si cet humain avait stagé, sur un des chemins touchés par la session, un contenu différent de son arbre de travail, cet état d'index est perdu (le contenu, lui, survit dans l'arbre).

- **Le tracker est exclu du rollback.** Ce qu'un rollback qui le restaurerait détruirait : `Failures:`, écrit juste avant lui — le compteur retomberait à zéro à chaque tentative et **aucun ticket ne serait jamais escaladé**, retry infini borné seulement par `ITER_CAP`. La règle est portée par une seule fonction, `gate_is_bookkeeping` (gate.sh), lue par le scope-guard **et** par le rollback ; deux copies auraient divergé. Nuance importante trouvée par le gate de mutation, voir plus bas : dans l'ordre livré, la boucle snapshote toujours l'arbre *avant* d'écrire le compteur, donc l'exclusion ne s'exerce jamais au seam process — c'est une garde pour le jour où cet ordre changera, et elle est tenue par un test dédié.

- **Commit sur vert : seulement ce que le scope-guard a approuvé.** `git commit-tree` + `update-ref` en plomberie plutôt que `git commit` : pas de hooks du projet hôte (un `pre-commit` qui reformate ou refuse casserait la garantie), pas de signature GPG, pas de template de message, et une suppression de fichier est enregistrée comme telle. Les chemins commités viennent du **tree que le scope-guard a jugé** (`RALPH_GATE_TREE`, nouveau, publié par la branche scope via un sidecar) : un artefact de build déposé par `TEST_CMD` après ce snapshot n'est pas le travail de l'itération et n'entre pas dans l'historique. Le `.scratch/` n'y entre jamais.

  Effet de bord voulu : l'index réel est resynchronisé (`git add -A -- $changed`) après le `update-ref`, sinon `git status` afficherait les fichiers commités comme « supprimés du staging ».

- **Message de commit en anglais**, comme le reste du pack, alors que `LANG_ARTIFACT` gouverne la prose durable du *projet cible*. Assumé : c'est une écriture de la boucle, pas de la session. À revoir avec [17] si la règle doit s'étendre aux commits que la boucle fabrique elle-même.

- **AC6 est garantie deux fois.** Le commit rend le travail durable, *et* le rollback ne peut de toute façon pas le détruire (il ne touche que le diff de la session courante). Conséquence pour les tests : « le fichier de l'itération 1 est encore là » ne prouve **pas** le commit — le test qui porte AC6 assert donc `git log -- src/alpha.txt`, pas la présence du fichier. C'est la mutation « a green iteration is not made durable » qui l'a exigé.

- **Une mutation de [05] est devenue vacuous, et c'est une vraie information.** « the scope-guard baseline is the last commit » (ramener `base` à `HEAD`) pointait sur le test d'accumulation (`previous one left in the tree`) : avec le commit-sur-vert, `HEAD` est redevenu une baseline correcte pour ce scénario précis, donc le test reste vert sans la garantie. L'entrée a été repointée sur `already dirty when the run started`, qui rougit toujours — un arbre sale **avant** le run n'est jamais couvert par un commit du run. La garantie « une itération n'est pas imputée du travail de la précédente » est désormais portée par trois choses au lieu d'une : le tree object, le commit sur vert, et le rollback.

- **`too-big` = la session a franchi la limite molle** (`over-soft-limit`). Le re-slice est une session fraîche de plus, passée par le même `loop_spawn` (extrait de `loop_spawn_session` : le prompt passe par un fichier et non un pipe, sinon `RALPH_SOFT_LIMIT_HIT` mourrait dans le sous-shell du pipeline). Elle écrit son plan dans un fichier **hors du dépôt** (`$TMPDIR`) et **ne crée aucun ticket** : c'est la boucle qui appelle `tracker_open_ticket`. Même règle que le marquage — une session qui écrit le tracker peut le figer dans un état qui n'a jamais été vrai, et ici elle s'octroierait en plus une write-surface que personne n'a vérifiée. Ce que la session de re-slice laisse dans le dépôt est rollbacké aussi.

- **Pourquoi le re-slice ne délègue pas à `to-tickets`, alors que l'AC dit « via `to-tickets` ».** Le skill **existe** dans ce dépôt (`.agents/skills/to-tickets/SKILL.md`, exposé par le lien `.claude/skills/to-tickets`) — une première rédaction de ce commentaire affirmait le contraire, sur la foi d'un `find -type f` qui ne suit pas les liens symboliques. Trois raisons, vérifiées, font que la boucle AFK ne peut pas s'en servir :

  1. **Son frontmatter porte `disable-model-invocation: true`** : un modèle ne peut pas l'invoquer. Seul un humain le déclenche, par `/to-tickets`. Déléguer voudrait donc dire faire du spawn de re-slice un `claude -p "/to-tickets …"`, une forme de spawn entièrement différente.
  2. **Son étape 5 publie elle-même dans le tracker** (« write one file per ticket under `.scratch/<feature-slug>/issues/` »). C'est exactement ce que la boucle doit interdire à une session : la validation du découpage (au moins deux blocs, AC présentes, write-surface incluse dans celle du parent) se fait **avant** création, parce que le tracker est hors de portée du rollback et qu'un ticket créé ne peut pas être décréé. Un skill qui publie d'abord inverse cet ordre.
  3. **Le skill ne fait pas partie du pack déposé** : ce qui est installé dans un projet cible est `loop.sh`, la config, `settings.json` et `lib/*.sh` (voir `harness__install_pack`). Les skills viennent de `skills-lock.json`, propre à ce dépôt. La boucle ne peut donc pas supposer sa présence chez l'hôte.

  Le contrat qu'il porte — découper en tranches livrables par une session fraîche, en préservant les AC — est donc écrit en ligne dans `failures__reslice_prompt`, et le format de plan reste la frontière que la boucle valide. Là où `to-tickets` est le bon outil, c'est la boucle humaine [16] : un humain l'invoque, relit, et sa publication directe est légitime puisqu'elle est validée par un humain. C'est le sens de la ligne de routage `too-big`→to-tickets de la spec.

- **Trou trouvé en vérifiant ce point, refermé : une session qui écrit le tracker elle-même n'était vue par personne.** Le prompt l'interdit, et jusqu'ici c'était toute l'application de la règle. Le scope-guard écarte `.scratch/<feature>/` comme bookkeeping de la boucle ([05]) et le rollback le laisse intact volontairement — donc un ticket écrit à la main par une session **survivait** à l'itération et rejoignait la frontière, avec la write-surface qu'elle s'était accordée. Un run se mettait alors à broyer un travail que personne n'a demandé, dans une surface que personne n'a vérifiée.

  Ce n'était pas propre au re-slice : la **session de delivery** est le cas fréquent, et l'écart date d'[05]. Le tracker étant un ensemble d'ids, le contrôle est une différence d'ensembles autour du spawn (`failures_tracker_snapshot` avant, `failures__strays` après). Tout id apparu part au puits humain avec `Escalation: decision` — un humain tranche s'il est légitime — et une note est posée sur le ticket qui a laissé faire. Deux points d'appel : la boucle après chaque session de delivery, et le re-slice, qui **refuse en plus le plan entier** (la sortie d'une session qui a franchi le seul contrôle non rattrapable ensuite ne mérite pas d'être lue, aussi propre soit-elle).

  Séparé du verdict du gate à dessein : le gate juge le code, ceci juge une entrée dans l'état propre de la boucle. Une itération peut donc être `resolved` tout en ayant fait quarantiner un ticket — le travail livré est bon, l'entrée illégitime est neutralisée.

- **Le plan est validé en bloc avant qu'un seul ticket soit créé** : au moins deux blocs, un slug et un titre exploitables, des AC présentes, et **chaque write-surface enfant incluse dans celle du parent**. Un plan qui élargit le contrat est refusé entier (escalade `too-big`) : la write-surface est ce sur quoi le scope-guard juge toutes les sessions suivantes, donc un plan qui en invente une ne se rattrape pas. La création est irréversible côté rollback (le tracker en est exclu par construction) — d'où le tout-ou-rien.

- **Branche défensive non atteignable depuis le seam process, assumée comme telle** : si `tracker_open_ticket` échoue pour *une partie* des blocs (répertoire de tickets soudain non inscriptible en plein milieu), le split a perdu les AC du bloc manquant et rien ne peut les rendre — le tracker est hors de portée du rollback par construction. Le code laisse alors le parent au humain avec une note listant ce qui a été créé, au lieu de le bloquer sur un split incomplet. Testable seulement dans le cas *total* (rien ne se crée → escalade, chemin déjà couvert) ; le cas partiel demanderait un échec sur un bloc et un succès sur l'autre, ce qu'aucun scénario ne produit. C'est une garde, pas une garantie testée.

- **Le parent d'un re-slice n'est ni résolu ni abandonné : il est bloqué sur ses enfants** (`tracker_block_on`, nouvelle opération de l'interface d'adaptateur) et revient en frontière quand ils sont tous `resolved`. Les deux alternatives sont pires : le marquer `resolved` serait un vert que personne n'a gagné et débloquerait ses dépendants avant que le travail existe ; le sortir de la frontière autrement bloquerait ses dépendants **pour toujours et en silence** (seul `resolved` déblo­que). Au retour, la session trouve le travail fait, n'écrit rien, et c'est son propre gate vert qui le clôt. Si le parent est encore trop gros, il est re-slicé à nouveau ; la terminaison vient du fait qu'un ticket qu'on ne peut plus découper produit un plan vide → escalade `too-big`.

- **Jeu fermé des raisons d'escalade utilisé ici** : `failed-impl` (gate rouge ou crash au-delà de `RETRY_N`), `decision` (débordement contractuel — deux tickets dessinés sur un même fichier, c'est un arbitrage humain, routé vers grilling par [16]), `too-big` (aucun découpage possible). `spec-gap` et `sign-off` restent pour [11] et [16].

- **`RETRY_N` compte des tentatives, pas des retries** : la comparaison est `Failures > RETRY_N`, donc `RETRY_N=2` donne 3 sessions (1 + 2 retries) avant escalade, et `RETRY_N=0` escalade à la première. Cohérent avec la formulation de l'AC ; le test le pin.

- **Interaction avec le détecteur stérile, à connaître** : avec les valeurs par défaut (`STERILE_K=3`, `RETRY_N=2`), un ticket qui échoue en boucle est escaladé **à sa 3ᵉ tentative**, exactement au moment où le run s'arrête pour stérilité. Le ticket est bien escaladé (l'escalade se fait pendant l'itération, l'arrêt est constaté au tour suivant) — mais avec `STERILE_K=1` ou `2`, un run peut s'arrêter avant d'avoir consommé les retries d'un ticket, qui reste alors `ready-for-agent` avec un `Failures:` partiel. Ce n'est pas un bug : c'est le garde-fou du run qui l'emporte sur la politique du ticket. Le run suivant reprend le compteur là où il en était, ce qui est la bonne sémantique pour un `Failures:` porté par le ticket.

- **Un ticket ré-injecté par la boucle humaine [16] garde son `Failures:`** et sera donc escaladé à la première tentative s'il était déjà au-delà de `RETRY_N`. C'est à [16] de remettre le compteur à zéro en ré-injectant (contrainte consignée là-bas).

- **Timeout de branche du gate livré** (trou connu ci-dessus) : `GATE_TIMEOUT` (défaut 1800 s, `0` = désactivé), un chien de garde par `gate_run` qui dort par tranches d'une seconde — pour ne laisser au pire qu'un `sleep` orphelin d'une seconde quand on le tue — puis descend l'**arbre de processus** de chaque branche (`ps -A -o pid= -o ppid=`, récursif : tuer le seul sous-shell laisserait la suite de tests qui pend tourner toute la nuit sur ses ports). Une branche tuée n'écrit pas de code de retour, et « pas de verdict » comptait déjà rouge : le timeout n'a donc pas besoin de verdict propre, seulement d'empêcher un run de pendre. Un timeout est classé `gate-red`, donc retryable — une suite qui pend peut pendre à cause du code que la session vient d'écrire.

  Résidu assumé : le chien de garde ne surveille **que le gate**. Une session `claude` qui pend sans émettre de token n'est bornée par rien (le filet [04] surveille les tokens, pas le temps). À traiter en [04] ou avec le budget [08].

- **Écart de write-surface, large.** Déclarée : `.claude/lib/failures.sh`, `test/failures.bats`. Réellement écrite : + `loop.sh` (une politique d'échec que la boucle n'appelle pas est du code mort — extraction de `loop_spawn`, snapshot `pre`, câblage des deux branches), + `gate.sh` (`RALPH_GATE_TREE`, `gate_is_bookkeeping`, timeout), + `tracker.sh`/`tracker-local.sh` (`tracker_block_on`), + `ralph.config.sh.example` et `test/smoke.bats` (`GATE_TIMEOUT`), + `test/canary.bats` (lever le `skip`, AC explicite), + `test/gate.bats`, `test/smart-zone.bats`, `test/loop-happy-path.bats` (des tests assertaient `ready-for-agent` là où la politique d'échec escalade maintenant — comportement placeholder de [03]/[04]/[05], remplacé, pas supprimé), + `test/mutate.sh` (le gate de mutation). - **Un `git rm --cached` a échoué en silence pendant une heure.** La branche `failed/<ticket>` embarquait tout `.scratch/` malgré le `git rm -r --cached` censé l'en retirer : git refuse de retirer un chemin dont le contenu stagé diffère à la fois de l'arbre de travail et de `HEAD` — ce qui est exactement le cas ici, puisque `Failures:` vient d'être écrit. Il fallait `-f`. Le `|| true` de la commande masquait l'échec ; c'est l'assertion « la branche ne contient pas `.scratch/` » qui l'a attrapé. Sans elle, chaque escalade aurait commité le flux de session complet (jusqu'à des dizaines de Mo) dans l'historique du projet cible.

- **Deux défauts trouvés en se demandant « et si git dit non ? », pas par la suite.** `set -euo pipefail` est actif dans `loop.sh` et les libs y sont sourcées : **toute** commande non gardée qui rend non-zéro tue le run entier, y compris à l'intérieur d'un `if`. Or `failures_make_durable` et `failures_preserve_attempt` rendent 1 sur plusieurs chemins réalistes. Conséquence avant correction : un dépôt cible où git refuse d'écrire une ref faisait **s'arrêter le run au premier ticket vert**, sans message utile. Les deux appels sont maintenant `|| true` — un avertissement, pas une fin de nuit — et deux tests pinnent le comportement avec des pannes que git produit vraiment :

  - un `refs/heads/main.lock` périmé (ce qu'un git tué laisse derrière lui) : plus aucun `update-ref` ne passe, donc aucune itération n'est durable ; le run doit dire « it is not durable » et broyer la frontière quand même ;
  - une branche nommée `failed` déjà présente : git ne peut alors pas créer `failed/<ticket>` (conflit de nom de ref) ; l'escalade doit quand même se poser, seule la branche forensique est perdue.

  À noter pour les tickets suivants : `tracker_mark_escalated`, `tracker_unclaim` et `tracker_mark_resolved` restent appelés **sans garde**, comme avant ce ticket — un échec d'écriture du tracker arrête donc le run. C'est cohérent (le tracker est la seule autorité d'état, continuer sur une écriture perdue serait pire) mais ce n'est écrit nulle part ailleurs.

- **Une mutation de ce ticket est restée vacuous deux fois, et la raison valait la trouvaille.** « le rollback réécrit le bookkeeping de la boucle » (retirer l'exclusion `.scratch/`) laissait le canari **et** le test de crash verts. Cause : la boucle prend son snapshot post-session **avant** d'écrire `Failures:` — sur le chemin gate rouge parce que le tree vient du gate, sur le chemin crash parce que `failures_handle` snapshote avant le compteur. Le fichier du ticket est donc identique des deux côtés du diff du rollback, et l'exclusion ne s'exerce jamais au seam process. Elle n'est pas inutile pour autant : elle est ce qui protège le compteur le jour où quelque chose écrit le tracker plus tôt (et sans elle, `Failures:` retomberait à zéro à chaque tentative — plus aucune escalade, jamais). Le test qui la porte pilote donc `failures_rollback` directement, avec un `tracker_bump_failures` entre les deux snapshots. C'est l'exception « unit » assumée du ticket, et elle est documentée dans le test.

Le gros du surcoût vient des sessions de re-slice (une session `claude` fake de plus par échec `too-big`), du test de timeout (une seconde de délai réel) et des appels git supplémentaires par itération.
- **Ce que la quarantaine ne couvre pas, et qui part en [21]** : elle compare des **ids**, donc elle voit un ticket *créé* par une session, pas un ticket *modifié*. Une session qui réécrit sa propre write-surface en `*` obtient encore un scope-guard vert (reproduit ; faux vert avec mécanisme). Ouvert en [21], avec le test `skip` correspondant dans le canari.
- **Défaut trouvé et corrigé le 28/07/2026, dans le commit sur vert livré ici : `git update-ref` était un write, pas un compare-and-swap.** `git update-ref -m … HEAD "$commit"` sans l'ancienne valeur écrase la ref quoi qu'il arrive. Conséquence, sondée : deux runs sur un même dépôt — un scénario à un `rm -rf` du verrou de run, qui vit dans le tracker et que rien ne gardait ([12]) — se commitent l'un sur l'autre, une itération verte disparaît de l'historique, et les deux runs rapportent `resolved`. Corrigé en passant `"$head"` (la valeur lue juste avant), ce qui fait refuser git si HEAD a bougé entre-temps ; `""` couvre le dépôt sans commit encore (« doit ne pas exister »), vérifié. C'est aussi ce qui rend inoffensive la fenêtre que le contrôle de verrou de [12] ne peut pas couvrir.

  Le test qui le porte (`a durable commit never overwrites a HEAD it did not read`) pilote un shim `git` transparent qui, sur le `commit-tree` précédant le commit durable, laisse un run concurrent commiter d'abord — la seule façon de se tenir dans la fenêtre exprès. **Et sa première version était vacuous** : la mutation écrivait `$commit` non échappé, que perl interpole en chaîne vide, donc le code muté était cassé plutôt que privé de sa garantie. Défaut du gate de mutation, pas du test — traité à part.
- **Contrainte posée par l'ouverture de [23] le 29/07/2026 : `failures_classify` gagnera une classe pour le timeout de session.** Le chien de garde livré ici borne les branches du gate ; le pendant manquant — une session `claude` qui pend sans émettre un token — est désormais porté par [23]. Ce qui atterrit ici : un timeout de session **ne doit pas** être classé comme `over-soft-limit`. Les deux tuent la session par SIGTERM, mais une session coupée pour contexte dit quelque chose sur la **taille du ticket** (`too-big`, donc re-découpage), alors qu'une session qui pend ne dit rien du tout : elle veut un retry en session fraîche jusqu'à `RETRY_N` puis `ready-for-human`. Réutiliser `too-big` par commodité ferait re-découper des tickets pour une raison qui n'a rien à voir avec leur taille, et le re-slice coûte une session `claude` de plus par échec.

- **Deux constats de la passe transversale du 29/07/2026, ouverts ailleurs.**

  1. **Le rollback ne peut pas défaire ce que le snapshot ne contient pas** — donc rien de ce que `.gitignore` couvre. Sondé sur une itération rouge : `src/alpha.txt` est bien restauré, `cache/payload` reste. « L'arbre est remis où la session l'a trouvé » est donc vrai *à l'exception d'un ensemble de chemins que personne n'énumère*. Ouvert en [24] ; noté ici parce que c'est `failures_rollback` qui porte la promesse.
  2. **`Failures:`, le compteur posé par ce ticket, n'est remis à zéro par personne** — ni `tracker_mark_resolved`, ni `tracker_mark_ready`. Sondé : un ticket peut être escaladé en `failed-impl` **après avoir été livré vert deux fois**. Ouvert en [26], avec le piège associé : remettre le compteur à zéro sur `unclaim` rouvrirait le re-broyage infini que `RETRY_N` existe pour empêcher, alors que le remettre à zéro sur `resolved` est sûr.

- **Ce que [35] a changé pour le parent d'un re-slice, livré le 04/08/2026.** Le commentaire de `failures_reslice` dit « le parent revient à la frontière et gagne son propre gate vert ». Depuis [35], une itération dont le gate ne voit changer aucun fichier est rouge (`delivery=red`) — et le parent d'un split est **exactement** ce cas par construction : le prompt de re-slice exige que chaque critère d'acceptation soit porté par un enfant, donc une fois les enfants résolus, une session sur le parent n'a plus rien à écrire. Le parent est donc retryé `RETRY_N` fois puis escaladé `nothing-delivered`, et le test `a slice too big for one session is cut up` l'asserte désormais ainsi.

  **Décision, et pourquoi ce n'est pas une régression.** Le vert que le parent obtenait avant était un tampon : ses trois branches objectives étaient vertes parce que les *enfants* avaient livré, pas lui. La phrase « il gagne son propre gate vert » décrivait un gate qui n'avait rien à juger. Et rien dans le pack ne vérifie que le split couvre le parent — `failures__plan_is_sound` contrôle la write-surface et la présence de critères, pas leur conservation ; c'est une règle du prompt, donc une ligne du tableau de la frontière de confiance. « Est-ce que ces deux morceaux valent le ticket d'origine » est donc une question d'humain, et l'escalade est le bon guichet : la note posée par [35] demande littéralement « pourquoi ce ticket ne fait-il rien faire à une session », dont la deuxième réponse est « le travail est déjà fait ». Le prix, écrit : `RETRY_N + 1` sessions dépensées avant l'escalade, sur un chemin déjà rare. Marquer le parent `resolved` à la place aurait été le faux livré que [35] existe pour refuser, obtenu par la porte d'à côté.
